# Функционально-воксельное ядро DCad — этап 1

Ветка: `feature/functional-voxel-kernel`, база: `Unified-CAD`. Проект: `src/DCad.FunctionalVoxel`, проверки: `tests/DCad.FunctionalVoxel.Tests`.

## Математическая модель

Это **не occupancy voxel** и не обычный SDF. Представляется аналитическое поле `u=f(x_0,...,x_(n-1))` и его локальные геометрические характеристики в каждой точке регулярной решётки аргументов. В каждой точке `p` известны `f(p)` и `g_i=∂f/∂x_i`. Локальная функция:

```text
L(x,u) = a0*x0 + ... + a(n-1)*x(n-1) + a(n)*u + a(n+1) = 0

b_i     = -g_i             i=0..n-1
b_n     = 1
b_(n+1) = sum_i g_i*p_i - f(p)
s       = sqrt(sum_(j=0)^(n+1) b_j^2)
a_j     = b_j/s             j=0..n+1

u(x) = -[a_(n+1) + sum_i a_i*x_i] / a_n
∂u/∂x_i = -a_i / a_n
```

Таким образом, для двух аргументов используются четыре М-образа, для трёх — пять. Числовой слой содержит один коэффициент локальной гиперплоскости на каждый воксель. Нормируется **весь однородный вектор коэффициентов**, включая свободный член; поэтому каждый коэффициент лежит в интервале [-1, 1]. Это важно для совместимости с опубликованной RGB-кодировкой. Операции над М-образами выполняются по восстановленным локальным функциям **без исходного аналитического выражения**.

Знак поля: `f >= 0` означает внутреннюю область. Величина поля не обязана быть подписанным расстоянием.

## Реализовано

| Компонент | Реализация | Проверка |
|---|---|---|
| Аналитические поля | `FunctionalField`, построитель выражений; скалярное значение, градиент, матрица Гессе средствами автоматического дифференцирования | полиномы, сфера, точные производные |
| Локальная функция | `LocalFunctionalPlane`: `n+2` коэффициента и обратное восстановление | касательная, градиент и единичная нормаль |
| М-образы | `FunctionalVoxelModel`: многоканальные массивы `double`, 1–4 измерения | размерность, восстановление в узлах |
| Упаковка | `EncodedMImages`: **каноническая** RGB24-кодировка `M = round((1+a)·(2²⁴−1)/2)` при `a∈[-1,1]`; отдельно экспериментальный режим авто-масштабирования | ошибка квантования `≤1/(2²⁴−1)` и обратный ход |
| Контроль точности RGB24 | `EncodedMImages.CompareWith(original)` возвращает максимальную абсолютную и относительную ошибку значения и абсолютную ошибку градиента | случай катастрофической потери точности при `f=10^9` |
| R-алгебра Рвачёва | R0 и параметр `alpha` для объединения, пересечения, вычитания; вычисление градиента по цепному правилу | топология знака, численное сравнение аналитики с операциями над М-образами |
| ФВ-арифметика | Сумма, разность, произведение, частное и модуль без исходной формулы; нулевая точка модуля и деление на ноль обрабатываются как особые случаи | проверка значений и градиентов на аналитических эталонах |
| Геометрические функции | плоскости, диск, шар, параллелепипед, цилиндр | тесты принадлежности |
| Проекция/перенос аргументов | `MapArguments` с произвольной аффинной матрицей, `Lift` | цепное правило до вторых производных |
| Дифференцирование | аналитически до второго порядка; по коэффициентам М-образов — первый порядок | полиномы |
| Численное интегрирование | метод трапеций вдоль оси, условие Коши в первом центре каждой строки | точная для линейного примера квадратная первообразная |
| Объём/площадь области | подсчёт положительных центров × мера ячейки | сходимость к объёму шара |
| Приближённая реконструкция между узлами | интерполяция локальных гиперплоскостей | линейная функция |
| Геометрическое выделение поверхности | `FunctionalIsoSurface.Extract` → общий `DCad.Core.Mesh3d`, согласованная тетраэдризация | замкнутость, winding, площадь и объём сферы |
| Базовый локальный поиск | `FunctionalVoxelLocalSearch.Minimize`: градиентная приоритизация соседей, знак допустимой области, критерий локального минимума | минимум выпуклого квадратичного поля с ограничением и без |

Тесты исполняются отдельно для Linux и Windows через `.github/workflows/functional-voxel-ci.yml`.

## Пример для будущего CAD

```csharp
using DCad.FunctionalVoxel;
using DCad.Core;

var sphere = FunctionalField.Sphere(0, 0, 0, 20);
var hole = FunctionalField.CylinderZ(0, 0, 5, -25, 25);
var part = sphere.Difference(hole);

var grid = new FunctionalGrid(
    new[] { -25.0, -25.0, -25.0 },
    new[] { 1.0, 1.0, 1.0 },
    new[] { 50, 50, 50 });

var model = FunctionalVoxelModel.Sample(part, grid);
var images = model.EncodeRgb24();          // 5 M-образов
var restored = images.ToModel();            // декодирование слоёв
var mesh = FunctionalIsoSurface.Extract(restored);
if (mesh is not null)
{
    var diagnostics = MeshValidator.Validate(mesh);
    Console.WriteLine($"Triangles = {mesh.Triangles.Count}, volume = {mesh.SignedVolume()}");
}
```


## Перепроверка по первоисточнику: 12 октября 2026

В работе А.В. Толока и Н.Б. Толок «Проекционный принцип построения функционально-воксельных моделей», *Онтология проектирования*, 2025, т. 15, № 4, с. 525–526 (рис. 4) приведены:
- локальный закон `n1*x + n2*y + n3*z + n4 = 0` для `z=f(x,y)` — четыре канала;
- нормированные однородные коэффициенты `n_i` в диапазоне `[-1,1]`;
- кодировка `M_i = P*(1+n_i)/2`, декодировка `n_i=(2*M_i-P)/P`, число оттенков RGB `P=16777216`.

В прежнем коммите нормировалась **только** градиентная часть без свободного члена, а диапазоны цветов подбирались отдельно по каждому М-образу. Это было математически восстанавливаемым представлением, но **не** опубликованной схемой кодирования. Порядок исправлен: полный однородный вектор нормируется и канонический режим закреплён за `EncodeRgb24`. Альтернативная инженерная калибровка оставлена только как `EncodeRgb24Calibrated`. Из-за `P-1` вместо `P` сохраняется симметричное отображение двух концов интервала; это отличие обозначено явно.

## Результаты второй ревизии ядра (2026-10-12)

Повторная сверка со страницами 525–526 статьи 2025 года выявила и исправила различие между нормировкой полного однородного вектора и нормировкой одной градиентной части; восстановлен научный смысл фиксированной палитры `[-1,+1]`. Добавлены независимые тесты арифметики и составной геометрии с отверстием, а также проверка неустойчивости RGB-квантования для очень больших значений.

**Критическое ограничение цветовой модели:** даже если каждый коэффициент закодирован с погрешностью не более `1/(2^24-1)`, реконструированное значение `u = -(Σa_i x_i+a_const)/a_u` может иметь огромную абсолютную ошибку при малом `a_u`. Например, константа `u=10^9` имеет очень малый однородный коэффициент `a_u`; стандартный RGB24 не в состоянии обеспечить его точное представление. Новая функция `CompareWith` позволяет количественно обнаружить подобные случаи. Поэтому `double`-каналы остаются основным точным представлением, RGB24 — внешним дискретным форматом с проверкой качества.

**Вердикт ревизии:** базовое ФВ-ядро проверяется от конструктивных формул до сетки изоповерхности, но все опубликованные ветви авторских исследований полностью не реализованы. Научное соответствие отдельных производных, интегральных, проекционных и оптимизационных алгоритмов требует дополнительной эталонной валидации.

## Принципиальные ограничения и следующие этапы

1. **Не доказана побитовая совместимость с авторским ПО.** Формулы локальной гиперплоскости и R0 математически сопоставимы с опубликованным подходом, но выбор нормализации, сетки, интерполяции и диапазонов кодирования является инженерной реализацией. Нормализация полного однородного вектора и формула `Mi=P(1+ni)/2` сверены со статьёй 2025 года (см. рис. 4, с. 526). В публикации `P=2²⁴`, однако RGB24 имеет максимальный **код** `2²⁴−1`; в коде принято отображение **обеих** границ в допустимые целые коды через `P-1`. Это инженерное уточнение, которое нужно отдельно сопоставить с оригинальным бинарным форматом. Указание «точность до 5-го знака» не следует автоматически из 24-битной упаковки без выбранного диапазона.
2. **Сингулярности.** В точке, где оба операнда R0 равны нулю, нормаль может быть неопределена. Программа явно сообщает ошибку, а не фабрикует производную. Поверхность, проходящая строго через центр ячейки, также требует иной политики обработки, пока извлечение сетки сигнализирует ошибку.
3. **Точность производных.** Хранение локальной гиперплоскости даёт точную первую производную относительно исходной аналитической функции в центре выборки. Вторые производные по М-образам вычисляются конечными разностями; третий аналитический порядок пока не реализован.
4. **Интегрирование** численное: граница Коши задана в первом центре линии, не на внешней границе. Нет универсального решателя ОДУ/ДУЧП по методике работ 2022–2024.
5. **Проекционный принцип 2025** реализован только на уровне подъёма измерений и аффинного преобразования аргументов. Автоматического восстановления 3D по комплекту чертежей, законов вращения для сложных профилей, комбинаторного анализа проекций нет.
6. **Другие направления научной школы:** реализован лишь базовый локальный градиентно-ориентированный перебор по соседним вокселям, **не точное воспроизведение** алгоритма из статьи 2017 года. Роботы/траектории, скелетизация, напряжения, интегральные характеристики поверхности, произвольные нелинейные задачи, адаптивная разреженная решётка не заявляются реализованными.
7. **Извлечение поверхности** — дискретная полигональная аппроксимация; не сертифицировано на вырожденных/самопересекающихся объектах. Это не заменяет геометрическое ФВ-представление.
8. Интерактивный инженерный интерфейс теперь реализован отдельно в `src/DCad.FunctionalVoxel.Viewer` и подключён к `DCad.sln`. Он визуализирует выбранные 3D-сечения, F и M0–M4, показывает исходную RGB24-кодировку и диагностическую псевдоцветовую карту. Он **не** реализует все методы из научных публикаций. Parser языка `.dcad` всё ещё не использует ФВМ.

Дополнительные инженерные части ядра `FunctionalIsoSurface` (тетраэдральное выделение поверхности), регулярная `double`-сетка, GDI-рендерер и объём по центрам ячеек — **самостоятельные программные решения**, не заявляются идентичными авторским алгоритмам ФВМ.

Научное соответствие базового аппарата **частичное и содержательное**, полного подтверждения всех ответвлений нет. По сравнению с формулой статьи 2025 года `Mi=P(1+ni)/2`, где `P=2^24`, в RGB24-кодировании программно используется `P-1`, чтобы корректно отобразить обе границы в диапазон `0..2^24-1`. Для побитовой совместимости с авторским ПО нужен оригинальный формат.
